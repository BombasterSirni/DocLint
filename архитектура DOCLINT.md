**АРХИТЕКТУРА И ТЕХНИЧЕСКОЕ ЗАДАНИЕ DOCLINT**

**1: ДЕКОМПОЗИЦИЯ БИЗНЕС-ТРЕБОВАНИЙ**

*Принцип: пользователь получает понятный список ошибок оформления своего .docx по выбранному профилю, а файл остаётся на его компьютере.*

**1.1. Аудит бизнес-гипотезы**

* **Три функции MVP:**

  * Проверка документа: принять .docx и профиль, вычислить оформление обычных абзацев, сравнить с правилами и вернуть нарушения.

  * Отчёт: показать место, найденное и требуемое значение и подсказку, объединить соседние нарушения. Профиль: два пресета или свой с локальным хранением и обменом JSON.

* **Границы MVP:**

  * Проверять поля страницы, шрифт, размер, интервал, отступ первой строки и выравнивание; это прямо соответствует бизнес-гипотезе.

  * **Пропускать титульный лист до первого явного разрыва страницы, заголовки, оглавление, таблицы и пустые абзацы. Не менять исходный документ.**

* **Нефункциональные требования:**

  * Ориентир: документ на 40 страниц обрабатывается за 10 секунд на обычном ноутбуке; показать ход проверки и не блокировать интерфейс.

  * Файл читается в браузере без отправки на сервер; нет регистрации, аналитики, внешних API и хранения текста работы.

  * В LocalStorage хранятся только пользовательские профили. Отчёт живёт до новой проверки или закрытия вкладки.

**1.2. Анализ ограничений и границ**

* **Внешние ограничения:**

  * Статический сайт GitHub Pages; JSZip поставляется локальным файлом. Для проверки не требуется интернет после загрузки сайта.

  * Один разработчик реализует MVP за неделю; используются HTML, CSS, JavaScript, DOMParser и node \--test без серверной инфраструктуры.

* **Границы данных:**

  * Вход: один файл .docx и профиль. Выход: отчёт на странице; печать или сохранение PDF средствами браузера.

  * Ограничение интерфейса: один файл за раз, до 20 МБ. Размер и тип проверяются до распаковки; лимит защищает браузер от зависания.

  * После проверки временные XML-данные и текст документа не сохраняются; новый файл заменяет предыдущий отчёт.

**2: ПРОЕКТИРОВАНИЕ АРХИТЕКТУРЫ**

*Принцип: все функции MVP выполняются на стороне клиента; лишние компоненты не вводятся.*

**2.1. Выбор компонентного состава**

* **Клиентская часть (интерфейс):**

  * Одна адаптивная страница: выбор профиля, область загрузки, отчёт и форма профиля.

  * Обычный JavaScript без фреймворка ускоряет разработку и упрощает публикацию на GitHub Pages.

* **Прикладная логика:**

  * Модули file-reader, docx-parser, style-resolver, rules, report и profiles работают в браузере; серверной части нет.

  * UI вызывает функции модулей напрямую. Модули возвращают данные или типизированную ошибку; сетевых запросов нет.

* **Хранилище данных:**

  * Два встроенных профиля заданы в коде; пользовательские профили сохраняются в LocalStorage с версией схемы.

  * Исходный .docx и результаты проверки находятся только в памяти вкладки. База данных не нужна.

* **Вычисления и интеграции:**

  * JSZip распаковывает OOXML, DOMParser читает XML, правила сравнивают значения; моделей ИИ и внешних API нет.

**2.2. Архитектурная схема**

* **Компоненты и связи:**

  * Пользователь → страница → проверка файла → JSZip/DOMParser → нормализация стилей → правила профиля → отчёт → пользователь.

  * Форма профиля ↔ LocalStorage; импорт/экспорт ↔ локальный JSON. GitHub Pages отдаёт только статические файлы приложения.

* **Поток данных:**

  * 1\) выбрать профиль и .docx; 2\) проверить тип и размер; 3\) извлечь document.xml, styles.xml и theme1.xml при наличии.

  * 4\) определить эффективные свойства абзацев; 5\) исключить элементы вне MVP; 6\) сравнить с профилем; 7\) сгруппировать нарушения и отобразить отчёт.

**2.3. Проектирование модели данных**

* **Сущности в памяти:**

  * Profile: id, name, version, marginsMm, fontFamily, minFontPt, lineSpacing, firstLineMm, alignment; preset или пользовательский.

  * ParagraphRecord: index, preview, properties, sectionIndex, skippedReason; Violation: paragraphIndex, ruleId, actual, expected, hint; Report: summary, violations, skippedCount.

* **Правила целостности:**

  * У профиля уникальный id; у нарушения ключ — пара paragraphIndex и ruleId. Встроенные профили нельзя перезаписать.

  * Все поля профиля обязательны; значения чисел конечны и положительны, кроме допустимого нулевого отступа; неизвестные поля JSON игнорируются.

**3: РАЗРАБОТКА ТЕХНИЧЕСКОГО ЗАДАНИЯ**

*Принцип: вход, выход, исключения и критерии проверки определены до начала кодирования.*

**3.1. Спецификация контрактов взаимодействия**

* **Публичные функции модулей:**

  * checkDocument(file, profile) → Promise\<Report\>; validateProfile(json) → Profile; saveProfile(profile), exportProfile(id), importProfile(file).

  * Report: totalChecked, skippedCount, countsByRule, violations\[\]. Нарушение содержит paragraphIndex, preview, ruleId, actual, expected и hint.

  * Валидный вход: .docx 2 МБ и профиль «Типовая методичка (кегль 14)». Невалидный: .doc, ZIP без word/document.xml или JSON без marginsMm.

* **Обработка ошибок:**

  * При неверном типе, размере, повреждённом ZIP или некорректном профиле показывать сообщение и сохранять возможность выбрать другой файл; при неизвестном значении оформления пропускать правило и считать его непроверенным.

  * Единый формат: {code, message, details}. Коды: INVALID\_FILE, FILE\_TOO\_LARGE, INVALID\_DOCX, INVALID\_PROFILE, CHECK\_FAILED. В UI показывать понятный message.

**3.2. Детализация алгоритмических процессов**

* **Логика проверки:**

  * Извлечь только необходимые XML; порядок абзацев брать из document.xml. Пропустить таблицы, заголовки, оглавление, пустые абзацы и часть до первого явного разрыва страницы.

  * Свойства вычислять в порядке: defaults → цепочка basedOn стиля → прямое форматирование абзаца → прямое форматирование фрагмента; учитывать theme1.xml, twips и half-points.

  * Сравнивать с допуском: размеры ±0,5 мм, кегль ±0,5 пт, интервал ±0,05; неизвестное не считать ошибкой. Сортировать отчёт по месту, объединять одинаковый ruleId и actual в соседних абзацах.

* **Конфигурации:**

  * Пресеты и тексты подсказок держать в отдельных JS-модулях; версия схемы профиля — 1\. Пресет ГОСТ: поля 30/15/20/20 мм, Times New Roman, минимум 12 пт, интервал 1,5, отступ 12,5 мм, по ширине.

**3.3. Проектирование интерфейса**

* **Ключевые области страницы:**

  * Верх: название, краткое обещание и указание «файл не покидает компьютер»; далее выбор профиля и кнопка «Проверить пример».

  * Центр: зона перетаскивания и выбора .docx, информация о лимите 20 МБ; форма профиля открывается отдельным блоком на той же странице.

  * Низ: сводка по правилам, фильтр, карточки нарушений, кнопка печати. В карточке — абзац, найденное/нужное значение и шаг исправления в Word.

* **Состояния интерфейса:**

  * Загрузка: индикатор «Проверяем документ…», повторный запуск недоступен до завершения текущей проверки.

  * Успех: число проверенных и пропущенных абзацев; если нарушений нет, сообщить о результатах только в пределах проверяемых правил.

  * Ошибка: короткое сообщение с причиной и действием — выбрать .docx, уменьшить файл или исправить JSON профиля.

  * Пустое состояние: приглашение выбрать файл или открыть демонстрационный пример.

**4: ПЛАНИРОВАНИЕ РЕАЛИЗАЦИИ**

*Принцип: первая неделя — гипотеза, вторая — это ТЗ, третья — реализация и проверка MVP одним разработчиком.*

**4.1. Декомпозиция на задачи (WBS)**

* **Задачи разработчика на третью неделю:**

  * День 1, 5 ч: репозиторий, страница, локальный JSZip, сборка тестов и публикация черновика.

  * Дни 2–3, 12 ч: разбор OOXML, наследование стилей, единицы измерения, правила и тестовые документы.

  * День 4, 5 ч: карточки отчёта, группировка, сводка и фильтры.

  * День 5, 5 ч: пресеты, форма профиля, LocalStorage, проверка и импорт/экспорт JSON.

  * День 6, 5 ч: интеграция, демонстрационный пример, проверка файлов Word, Google Docs и LibreOffice.

  * День 7, 4 ч: исправления, инструкция, README и публикация на GitHub Pages.

* **Итого 36 часов разработки. Участники 1 и 2 помогают с проверкой сценариев и демонстрацией, не блокируя разработчика.**

* **Критический путь: парсер → разрешение стилей → правила → отчёт. Профили и интерфейс можно готовить параллельно с парсером.**

**5: ФИНАЛИЗАЦИЯ И ПЕРЕДАЧА**

**5.1. Сборка пакета документации**

Состав передачи:

1. **Архитектурная схема: цепочка компонентов и потоков в разделе 2.2.**

2. **Модель данных: Profile, ParagraphRecord, Violation и Report в разделе 2.3.**

3. **Контракты: сигнатуры функций, схемы входа/выхода и коды ошибок в разделе 3.1.**

4. **Алгоритм: порядок чтения OOXML, приоритет стилей, правила исключений и допуски в разделе 3.2.**

5. **Интерфейс: области страницы и четыре состояния в разделе 3.3.**

6. **План работ: дневные задачи, часы и зависимости в разделе 4.1.**

**5.2. Проверка качества (Self-Check)**

* Все три функции MVP покрыты: проверка, отчёт и профиль кафедры.

* Сервер, база данных, ИИ, оплата и расширенные проверки не входят в MVP.

* Граничные случаи и ошибки описаны: неверный файл, большой файл, повреждённый DOCX, неизвестный стиль, неверный JSON.

* План на 36 часов оставляет ограниченный резерв; при задержке сначала сокращать оформление UI, сохраняя три функции MVP.
